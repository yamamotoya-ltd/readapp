# ステップ 1 実装計画：本文貼り付け → 専用ポッドキャスト

- 設計書: `docs/superpowers/specs/2026-10-28-readapp-design.md`
- ゴール: 入力画面に本文を貼る → 数分後に Apple Podcasts の非公開番組に新しい回が届く。月 90 万字で自動停止。
- 範囲外（ステップ 2 以降）: URL 抽出、PDF、5 万字超の長文、削除、要約、メール取り込み。

## 1. 技術の前提（確認済み）

- Google Cloud TTS: 1 リクエストあたりの入力は 5,000 バイトまで（変更不可）。Chirp 3 のレート上限は 200 回/分。
- Cloudflare Queues: Workers 無料プランで 1 日 10,000 オペレーションまで、メッセージの保持は最大 24 時間。
- Workers 無料プラン: 1 回の実行で外部呼び出し（subrequest）は 50 回まで、CPU 時間は 10ms まで。→ 1 回の実行で TTS を呼ぶのは 1 回だけにし、重い処理は Queue で分割する。
- 実装時に確認すること（タスク 0）: TTS が API キー認証で使えること、MP3 出力、正確な声の名前（`voices:list` で確認）。

## 2. 処理の流れ

```
POST /api/episodes（本文, タイトル任意）
  ├ 言語判別 → 分割（各 4,500 バイト以下・文の区切りで切る）
  ├ 上限チェックと予約（D1 で 1 文で原子的に加算。超えるなら 400 を返して終了）
  ├ episodes に status=processing, total_chunks=N で登録。分割した本文は R2 の chunks/<id>.json に保存
  └ Queue に {episodeId, index: 0} を送信 → 202 を返す

Queue 消費（1 メッセージ = 1 分割、max_batch_size=1）
  ├ chunk[index] を TTS に送り、MP3 を R2 の parts/<id>/<index>.mp3 に保存
  ├ 次があれば {episodeId, index+1} を送信（順番に連鎖させるので競合しない）
  └ 最後なら {episodeId, assemble:true} を送信

組み立て（assemble）
  ├ parts を順に読んで連結 → audio/<id>.mp3 に保存。再生時間は MP3 のフレームヘッダから計算
  ├ episodes を done にし、audio_bytes と duration_sec を記録
  └ parts/<id>/ と chunks/<id>.json を削除（R2 の一括削除を使い、外部呼び出しは 1 回で済ませる）

失敗時: Queue の自動再試行（max_retries=3）。最後の試行でも失敗したら status=failed と error を記録して ack。
再実行: POST /api/episodes/:id/retry で、失敗した index から再送する。
```

月の文字数: 登録時に全体を予約する。再試行で再送した分割の文字数も加算する（Google が再送分も課金するため、少なめには数えない）。月の区切りは米国太平洋時間の暦月とする。

```

```

## 5. レビューの観点（M が毎回確認すること）

- 本物の TTS をテストから呼んでいないか
- 上限チェックを迂回できる経路がないか（再試行の経路も含む）
- `/feed` と `/audio` 以外がすべて Access で守られているか
- 秘密（API キー、トークン）がコードやログに出ていないか
- 1 回の実行で外部呼び出しが 50 回を超えないか（5 万字 ÷ 約 1,500 字 ≒ 34 分割。組み立て時の R2 読み出しが最大の山）
